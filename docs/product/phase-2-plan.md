# برنامه اجرایی فاز ۲: LMS و تجارت

- **وضعیت:** آماده اجرا (۱۴۰۵/۰۷/۱۰، 2026-10-02)
- **پیش‌نیاز:** انتشار v0.3.0 (طراحی v2)
- **معماری:** [ADR-0008](../decisions/ADR-0008-lms-and-commerce.md)
- **منبع حقیقت استوری‌ها:** [backlog.yaml](../backlog/backlog.yaml) (EPIC-28 تا EPIC-32، به‌علاوه ST-07.03 و ST-20.02)؛ همگام‌سازی با `pnpm backlog:sync`

## ۱. هدف

فاز ۱ کاتالوگ دوره، سفارش و پرداخت آزمایشی را تحویل داد، ولی پرداخت موفق هنوز به هیچ نتیجه‌ای نمی‌رسد. دوره درس ندارد و کسی ثبت‌نام نمی‌شود. هدف فاز ۲ این است که سفر کامل آموزش آنلاین کار کند:

```text
کاتالوگ → خرید (یا ثبت‌نام رایگان) → پرداخت → ثبت‌نام خودکار → یادگیری → ثبت پیشرفت → تکمیل دوره
```

معیار موفقیت فاز ۲ (همه با درگاه آزمایشی تا پاسخ OQ-09):

1. کاربر در دوره رایگان با یک کلیک ثبت‌نام می‌کند و درس‌ها را می‌بیند.
2. کاربر دوره پولی را می‌خرد و پس از verify سمت سرور، دقیقاً یک ثبت‌نام برایش ساخته می‌شود؛ حتی اگر سرور وسط کار راه‌اندازی مجدد شود.
3. محتوای درس (متن، فایل، ویدئو) فقط برای دانشجوی مجاز و با لینک کوتاه‌مدت در دسترس است.
4. پیشرفت دانشجو ثبت و درصد تکمیل نمایش داده می‌شود.
5. کارکنان سرفصل، ثبت‌نام‌ها، فروش و پرداخت‌های نیمه‌کاره را مدیریت می‌کنند.
6. اعلان‌های تراکنشی (پرداخت، ثبت‌نام، تکمیل) واقعاً ایمیل می‌شوند و قابل retry هستند.

## ۲. وضعیت فعلی (بررسی کد، ۱۴۰۵/۰۷/۱۰)

| بخش             | موجود                                                                                      | کمبود برای فاز ۲                                                     |
| --------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| `learning`      | Course، Instructor، API کاتالوگ و ویرایش، قیمت ریالی (null = «استعلام»)                    | بخش، درس، ثبت‌نام، پیشرفت، نظر                                       |
| `orders`        | Order، OrderItem (فقط COURSE)، PaymentAttempt، callback idempotent، verify سمت سرور، Audit | fulfillment پس از پرداخت، تطبیق تلاش‌های INITIATED، رسید، گزارش فروش |
| `payments`      | port `PaymentGateway` با سقف timeout، adapter آزمایشی و disabled                           | adapter واقعی (OQ-09)، تست قرارداد مشترک                             |
| `notifications` | port `NotificationProvider`، adapter لاگ، inbox داخل سایت                                  | صف ارسال و retry، ایمیل SMTP، پیامک (OQ-08)، قالب‌ها                 |
| `files`         | ذخیره خصوصی، لینک امضاشده، سقف ۸ مگابایت                                                   | نوع فایل درس، سقف جدا برای ویدئو، پخش با Range                       |
| وب              | دکمه خرید، صفحه سفارش‌ها، درگاه آزمایشی، فرم درخواست ثبت‌نام                               | ویرایشگر سرفصل، دوره‌های من، صفحه پخش، رسید                          |
| RBAC            | `catalog:manage`، `orders:read-all`؛ نقش‌های student و instructor بدون مجوز                | `enrollments:manage`، `reviews:moderate`                             |

نکته معماری: ماژول `orders` همین حالا به `learning` وابسته است (خواندن قیمت دوره). بنابراین ثبت‌نام پس از پرداخت باید از سمت `orders` و با سرویس صادرشده `learning` انجام شود، نه برعکس. جزئیات در ADR-0008 آمده است.

## ۳. دامنه فاز ۲

**داخل دامنه:** سرفصل و درس، تحویل امن محتوای درس، ثبت‌نام (رایگان، خرید، دستی)، پیشرفت و تکمیل، fulfillment سفارش، تطبیق پرداخت، رسید پرداخت، گزارش فروش، مدیریت ثبت‌نام، صف و ایمیل اعلان، قالب‌های تراکنشی، نظر دوره با تأیید، port تحلیل بازدید، آزمون امنیتی و انتشار v0.4.0.

**منتظر تصمیم (طراحی و استوری آماده، پیاده‌سازی پس از پاسخ):** درگاه واقعی (OQ-09)، پیامک (OQ-08)، ورود با OTP (OQ-20)، گواهینامه (OQ-03)، استرداد (OQ-23)، کد تخفیف (OQ-31)، فاکتور رسمی (OQ-29)، جلسات حضوری (OQ-30)، فضای کار مدرس (OQ-33).

**خارج از فاز ۲:** آزمون و تکلیف (quiz/assignment)، کلاس زنده، انجمن گفت‌وگو، اشتراک ماهانه، اپلیکیشن موبایل (فاز ۹)، و هر چیزی از فازهای ۳ تا ۸.

## ۴. تصمیم‌های معماری (خلاصه ADR-0008)

1. مالکیت جدول‌ها: `learning` مالک بخش، درس، ثبت‌نام و پیشرفت است؛ `orders` مالک سفارش، پرداخت و fulfillment.
2. fulfillment با outbox: در همان تراکنش PAID یک ردیف `OrderFulfillment` نوشته می‌شود و پردازشگر با retry آن را به ثبت‌نام تبدیل می‌کند. ثبت‌نام idempotent است (یکتایی کاربر و دوره).
3. یک سیاست دسترسی خالص (`canAccessLesson`) برای همه endpointهای درس و ویدئو، با تست منفی.
4. ویدئو پشت port `VideoHostingProvider`؛ adapter اول روی ذخیره‌ساز خصوصی فعلی با لینک کوتاه‌مدت.
5. قانون‌های تعیین‌نشده خاموش می‌مانند و حدس زده نمی‌شوند.

## ۹. امنیت و کیفیت

- هر endpoint درس، ویدئو، پیشرفت و رسید تست منفی دسترسی دارد (کاربر دیگر، ثبت‌نام لغوشده، دوره پیش‌نویس).
- لینک ویدئو کوتاه‌مدت و امضاشده است؛ هیچ مسیر عمومی مستقیم به فایل درس وجود ندارد.
- مبالغ همیشه ریال صحیح (`bigint`/`Decimal`) هستند؛ محاسبه‌های مالی تابع خالص با تست مرزی دارند.
- رویدادهای ثبت‌نام، لغو، تطبیق پرداخت، خروجی CSV و تأیید نظر در Audit Log ثبت می‌شوند.
- Definition of Done همان [بخش ۶ implementation-plan](implementation-plan.md) است و `pnpm verify` و Playwright پیش از هر PR سبز است.
